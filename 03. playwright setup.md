# Overview

The pipeline drives portals through a real browser. All portal sessions live in one dedicated profile, kept apart from the personal Chrome profile, so any script that opens this profile is already logged in everywhere.

# Components

| Component | Location | Role |
|---|---|---|
| Browser profile | `~/.playwright-profiles/jobs` | Holds every portal session, cookies and storage |
| Browser binary | Google Chrome 152 at `/usr/bin/google-chrome` | The only binary that opens the profile |
| playwright-cli | global npm install, symlinked in `~/.local/bin` | Manual logins in a visible window |
| Python Playwright | `~/job-application/.venv` | Scripted portal access |
| Session checker | `~/job-application/scripts/check_session.py` | Confirms the sessions are alive |

Python scripts open the profile like this.

```python
p.chromium.launch_persistent_context(
    user_data_dir="~/.playwright-profiles/jobs",  # expanded
    channel="chrome",
    headless=False,  # everything runs headed, see rule 6
)
```

# Rules

1. One browser binary per profile. Chrome 152 creates the profile and Chrome 152 drives it. Mixing binaries or profiles causes bot-protection flags and profile-format mismatches.
2. Logins use the portal's own email and password form. Google sign-in is unreliable in an automated browser. It was refused in a script-launched Chrome window and then succeeded in a headed playwright-cli session on this profile on 2026-09-17, where a Google session now lives. A passkey prompt in that window logged no available authenticator, so the account needs a password.
3. A human types the credentials in a visible window. Scripts never handle passwords.
4. The profile directory holds live session tokens. It stays out of git and carries `0700` permissions.
5. A session counts as valid only on positive evidence, which means the portal's session cookie exists and the logged-in page renders. A correct-looking URL proves nothing.
6. All portal access runs headed, in one browser instance with one tab per portal. Decided 2026-09-17 for uniformity. Naukri blocks headless anyway, and the profile's singleton lock allows only one instance at a time, so a single headed instance is the one code path that serves every portal.

# Procedures

## Log in to a portal

```bash
playwright-cli open <login-url> --profile=$HOME/.playwright-profiles/jobs --headed
# sign in manually in the window, then:
playwright-cli close
```

| Portal | Login URL | Note |
|---|---|---|
| LinkedIn | `https://www.linkedin.com/login` | |
| Naukri | `https://www.naukri.com/nlogin/login` | |
| Stepstone | `https://www.stepstone.de/candidate/login` | |
| Indeed | `https://secure.indeed.com/auth` | Passwordless, emails a one-time code, and may show a Cloudflare human check |

## Verify sessions

```bash
cd ~/job-application && .venv/bin/python scripts/check_session.py
```

Exit code 0 means every session is valid. A failing portal is named with its reason. The check runs headed like everything else, so a window opens briefly.

# Portal constraints

Everything runs headed under rule 6. The tolerance column records what each portal accepts, not how it is run.

| Portal | Session cookie | Headless tolerance | Notes |
|---|---|---|---|
| LinkedIn | `li_at` | Works | |
| Naukri | `nauk_at` | Blocked, Akamai serves Access Denied | The reason everything runs headed |
| Stepstone | `AuthCA`, short-lived at about 15 minutes, re-minted on visit from `AuthCARefresh` which lasts about 90 days | Works | A logged-in visit to the login URL redirects to `/profile`. Read the cookies only after visiting |
| Indeed | `PPID`, plus the `__Secure-PassportAuthProxy-*` tokens | Untested | Cloudflare-guarded. The homepage URL is identical logged in or out, so only the cookie proves login |

# Troubleshooting

| Symptom | Cause | What to do |
|---|---|---|
| Access Denied on every request, even in a normal window | The profile is flagged by the portal's bot protection | Do not debug the code. Test with a fresh empty profile. If that passes, clear the flagged portal's cookies and log in again |
| `ERR_HTTP2_PROTOCOL_ERROR` on navigation | A flagged profile when it persists, transient otherwise | Retry once. If it repeats, run `clear_naukri.py` in its default `--bot-only` mode and retry. That restored access on 2026-09-30 without costing the session |
| Failed to create a ProcessSingleton | The profile is already open in another browser instance | Close it with `playwright-cli close` or close the window, then retry |
| Google sign-in refuses with "This browser or app may not be secure" | Automated browser, which Google blocks | Use the portal's own login and set a password through the portal's reset flow if the account has none. Retrying the Google sign-in in a headed playwright-cli session on this profile has also worked. Passkey prompts found no authenticator |
| Session expired | Normal expiry | Run the login procedure for that portal again. The rest of the profile is unaffected |
