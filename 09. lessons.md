# LinkedIn

The reader is `worker_linkedin` in `scripts/sweep.py`, with the record parsing in `scripts/collect.py` as `linkedin_records`. The `LinkedIn` class in `collect.py` still holds the search-URL builder and the 1000 cap, and its DOM extraction is no longer used by the sweep.

## Step 1. Read the endpoint, not the rendered list

Changed 2026-09-30. The rendered list is virtualized, so a card's id exists before its content and the reader captured empty cards. One run gave 145 of 203 rows with no company, location or age. The search page builds itself from an endpoint, so the collector reads that.

```
https://www.linkedin.com/voyager/api/voyagerJobsDashJobCards
  ?decorationId=com.linkedin.voyager.dash.deco.jobs.search.JobSearchCardsCollection-220
  &count=25&q=jobSearch&start={START}
  &query=(origin:JOB_SEARCH_PAGE_OTHER_ENTRY,keywords:{KW},
          locationUnion:(seoLocation:(location:{LOC})),
          selectedFilters:(sortBy:List(DD),experience:List(2,3,4),
                           timePostedRange:List(r{SECONDS})),
          spellCorrectionEnabled:true)
```

The shape lives in `queries.yaml` as `api_template`. `url_template` stays as the human link.

## Step 2. Establish the session, then send the requests

Load `https://www.linkedin.com/jobs/` once. Take the token from the `JSESSIONID` cookie with quotes stripped. Send requests through the page's own request context so they carry the profile cookies.

| Header | Value |
|---|---|
| `csrf-token` | `JSESSIONID` value, unquoted |
| `x-restli-protocol-version` | `2.0.0` |
| `accept` | `application/vnd.linkedin.normalized+json+2.1` |

A 401 or 403 is a dead session, which is a portal failure and never a thin cell.

## Step 3. Read the records

Verified 2026-09-30. 25 records per page. `paging.total` is the claimed count and drifts, measured at 163, 179 and 180 on one cell minutes apart.

Records are in `included`. Two `JobPostingCard` objects exist per posting, so read only those whose `entityUrn` contains `JOBS_SEARCH`.

| Field | Source |
|---|---|
| id | `jobPostingUrn`, last segment, the dedup key |
| title | `jobPostingTitle` |
| company | `primaryDescription.text` |
| location | `secondaryDescription.text`, with workplace type in parentheses |
| posted at | `footerItems` entry of `type: LISTED_DATE`, field `timeAt`, epoch ms |
| reposted | matching `JobPosting` object's `repostedJob`, boolean |

0 of 25 fields missing. Freshness, reposts and workplace type all became checkable, and none of the three had a usable source before.

## Step 4. Page to the end and check completeness

Increase `start` by 25 until `start + 25` reaches the smaller of the claimed count and the 1000 cap, or a page returns nothing new. Pace a few seconds.

A page before the last returning fewer than 25 records fails the cell as `PAGE_SHORT`.

Records missing a title, company, location or timestamp are counted and reported with the cell.

## Step 5. The result count is capped at 1000

LinkedIn reports the true number of matches but pages through only the first 1000. The C++ Developer search for Germany over 48 hours reported 1000 and the run collected 975 before pages ran out. A cell whose claimed count reaches 1000 cannot be read past that point through one query. With the preferences applied, a query is unlikely to get near it.

## Step 6. Sparse searches include out-of-scope results

When a search has few genuine matches, LinkedIn fills the page with postings from outside the requested location. A Robotics Engineer search for Norway returned postings located in Germany, and the endpoint does the same, returning `European Union (Remote)` and `EMEA (Remote)` rows on a Denmark cell. These belong to their own location's search, so any check of what a cell should contain has to drop results whose location or age falls outside the cell's bounds first.

## Operating notes

- Access uses the pipeline profile at `~/.playwright-profiles/jobs` with `channel="chrome"`, one browser instance at a time.
- LinkedIn served results headless, but the pipeline runs headed for every portal under the decision in [03. playwright setup](03.%20playwright%20setup.md).
- The job id is the last segment of `jobPostingUrn`, the same number the DOM carried in `data-occludable-job-id`. It is the dedup key, and the posting page is `https://www.linkedin.com/jobs/view/{id}/`.

# Naukri

The unblock remedy is `scripts/clear_naukri.py`. The pacing protocol below is the access procedure and it is what keeps Naukri from blocking. The reader is `worker_naukri` in `scripts/sweep.py`, with the parsing in `scripts/collect.py` as `naukri_records`. The `Naukri` class in `collect.py` still pages by URL, which is the pattern that raised the flag, so it is not used by the sweep.

## Step 1. Build the search URL

The role and city sit in the path, and the filters are parameters.

```
https://www.naukri.com/{role-slug}-jobs-in-{city}?jobAge={DAYS}&experience={N}
```

| Parameter | Value to send | Meaning |
|---|---|---|
| `role-slug` | role phrase, lowercase, spaces to hyphens, such as `embedded-software-engineer` | keyword search over postings. The page header echoes what Naukri understood. Verified for 10 of 10 role and city combinations |
| `city` | `bengaluru`, `hyderabad`, `pune` | city-scoped results |
| `jobAge` | days, native values only | 1 and 7 work and show a chip. 2 is ignored silently, with no chip and no filtering. There is no native 48 hour form, so how the 48 hour preference gets encoded is not decided. Open |
| `experience` | one number | returns jobs whose required range contains that number of years. Adding `experience=2` cut 1908 results to 250, and every regular card's range contained 2, such as 2-7, 2-6 and 2-5 years. Which number encodes the under-five-years band is not decided. Open |
| salary | never used | a native facet with fixed bands of 15-25, 25-50, 50-75 and 75-100 Lakhs. Not used, because compensation is never filtered at the query. It is put to the user on the card instead |

Two role slugs do not survive. `R&D Engineer` becomes the tokens "r d engineer" and returned 12 results, and `C++ Developer` becomes "c developer" and returned 9. Their portal-native forms have to come from Naukri's own search box before those cells run. Open.

## Step 2. Read back what Naukri understood

Read the page rather than trusting the URL. Three read-backs are verified. The search header echoes the interpreted query and city. An applied filter shows an "Applied (n)" chip, and its absence means a parameter was ignored, which is how the dead `jobAge=2` was caught. The result count appears as "1 - 20 of N".

Counts are per-query and real, with one caveat. Broad engineer phrases match loosely and converge on large city pools, around 1900 for three different broad queries in Bengaluru, while specific phrases scale down to 147, 285 and 12.

## Step 3. Read the response, not the cards

Changed 2026-10-01. The card reader dropped the location on every row and put the experience range in the age column, so all 1080 rows lacked a posting age.

The page fetches `jobapi/v3/search`. The reader attaches a response handler for that path and reads what the page fetched for itself. A direct call is refused with HTTP 406 `recaptcha required`, since the page signs each request with an `nkparam` header, so `queries.yaml` records it as `api_response_match` and never as a URL to request.

Verified 2026-10-01. Twenty records per page, `noOfJobs` as the claimed count at 2921, 0 missing fields.

| Field | Source |
|---|---|
| id | `jobId`, the dedup key |
| title | `title` |
| company | `companyName` |
| location | `placeholders` entry of `type: location` |
| posted at | `createdDate`, epoch milliseconds |
| experience | `placeholders` entry of `type: experience`, or `experienceText` |
| salary | `placeholders` entry of `type: salary`, as the portal renders it |
| url | `jdURL`, appended to the host |

`jobDescription` is in the payload too, 264 to 4486 bytes, which would remove the paced second load per posting. Not used yet.

Freshness and compensation became checkable here, and `Not disclosed` is recorded as stated rather than inferred.

## Step 4. Paginate by clicking, never by URL

Page through by clicking the site's own Next control, with a randomised 15 to 35 second pause between pages, in one session and one tab. This ran clean twice back to back, 12 pages without keywords for 240 postings and 3 pages with a keyword for 60 postings, about 40 requests inside an hour with no anomalies. Rapid fresh URL loads are what raised the bot-protection flag, and roughly 5 seconds apart was enough to do it. Click-pagination at human pacing has never triggered it.

## Step 5. Stop on the first anomaly

The failure signatures are `ERR_HTTP2_PROTOCOL_ERROR` at connection level, or an Access Denied page. Either one ends the whole Naukri run at once. Retrying into a raised flag deepens it, and recovery takes hours.

If the block survives a cool-down, the deny state is in the profile's Naukri cookies. The same page loaded in a clean profile on the same machine and IP, which is what proved it. The remedy is `clear_naukri.py`.

Verified 2026-09-30, and this corrects the earlier description of the remedy. A sweep cell failed with `ERR_HTTP2_PROTOCOL_ERROR` on its first navigation and an immediate retry failed identically. `clear_naukri.py` in its default `--bot-only` mode found 22 `naukri.com` cookies and dropped three of them, `bm_mi`, `ak_bmsc` and `bm_sv`. The next retry returned `ok` with 1138 claimed and 60 collected. Three things follow. The deny verdict rides in the Akamai cookies alone, not in the session and not in the IP. The session survives the clear, so no re-login is needed and an unattended run can continue. No cool-down was needed, because the clear ran within minutes of the block. `--all` remains available and is certain to clear the state, but it drops the session and costs one manual re-login, so it is the second resort rather than the first.

The remedy is incomplete without a new connection, and that correction cost two test runs. The clear was verified through `clear_naukri.py`, which opens its own browser, so the retry that followed it got a fresh connection as a side effect. Inside a sweep the same cookies were dropped on the live context, the session survived, and the retry failed with the identical `ERR_HTTP2_PROTOCOL_ERROR`. `ERR_HTTP2_PROTOCOL_ERROR` is a connection-level fault and the poisoned HTTP/2 connection is reused by the same page, so the cookies are only half of it. The retry has to run on a page opened after the clear. With that added, six consecutive cells returned `ok` with 68 new rows where the first cell had failed outright.

This now runs unattended. `worker_naukri` in `scripts/sweep.py` attempts the entry navigation, and on either failure signature it calls `clear_bot_state`, opens a fresh page and retries once. The circuit breaker trips only when that retry fails too, so one protocol error no longer costs the other 29 cells. A bare retry without the clear is still forbidden, since retrying into a raised flag deepens it.

When that is still not enough, `scripts/recover_naukri.py` hands the portal to Antigravity. It reads the run log, and on a breaker trip it gives Antigravity this section to follow, with a closed list of commands it may run, namely `check_session.py`, `clear_naukri.py --bot-only` and `sweep.py --portal naukri`. It may not log in, because he types passwords himself in a visible window. It may not run `--all`, since that costs him a re-login and is his decision. It may not work around a block, change the pacing, touch another portal or edit a file. A portal that stays blocked after the documented remedy is recorded and left alone. The stage runs at 1b in `nightly.sh` and costs no Claude tokens.

The recovery was proved on 2026-10-12 and it found a fault in this very procedure. `clear_naukri.py --bot-only` is what this section has always told a reader to type, and the flag did not exist in the script, so the documented command exited 2 while the behaviour it names was the default. It is accepted explicitly now, because an instruction that cannot be typed is not a procedure.

## Operating notes

- Headed browser only. Headless requests get the Access Denied page even with a valid session.
- Access uses the pipeline profile at `~/.playwright-profiles/jobs` with `channel="chrome"`, one browser instance at a time.
- Login state is the `nauk_at` cookie. Re-establish a session with `playwright-cli open https://www.naukri.com/nlogin/login --profile=$HOME/.playwright-profiles/jobs --headed`, using the native email and password form.

# Stepstone

The reader is `worker_stepstone` in `scripts/sweep.py`, with the parsing in `scripts/collect.py` as `stepstone_records`. Verified on 2026-09-18 and 2026-09-19 through exhaustiveness on a full city cell, a 10-of-10 role sweep, facet discovery from the portal's own filter links, and keyword pagination. Stepstone has shown no bot-protection behaviour at 3 to 5 second pacing.

## Step 1. Build the search URL

```
https://www.stepstone.de/jobs/{role-slug}/in-{place}?ag={AGE}&page={N}
```

| Parameter | Value to send | Meaning |
|---|---|---|
| `role-slug` | role phrase, lowercase, spaces to hyphens | keyword search, verified for 10 of 10 roles. `R&D Engineer` degrades to "R D Engineer" with the ampersand lost, confirmed in the portal's own echo. How `C++ Developer` is interpreted is unresolved. Both need native forms before their cells run. Open |
| `place` | `deutschland`, or a city such as `kiel` | Stepstone covers the Germany preference |
| `ag` | `age_1` for 24 hours or `age_7` for 7 days, and nothing else | native freshness values. There is no 48 hour form, so how the 48 hour preference gets encoded is not decided. Open |
| `page` | `1`, `2` and so on | pagination, 25 genuine results per page |

Stepstone has no seniority facet. The full list the page has is age, application method, detected language, disciplines, numeric skill ids, work-from-home and worktypes, so seniority has to be handled after the fetch. Salary appears as a display rather than a filter link, so compensation is handled after the fetch as well. A language facet exists as `fdl=en` and is unused.

## Step 2. Read the count, and ignore the echo banner

The count appears as "N Treffer" or "N Jobs" and is per-query, measured across roles from 5 to 225 in a 24 hour window.

The "Suchst du noch nach X?" banner echoes the previous search rather than the current one. A Firmware query showed the prior query's text. Never read it as a confirmation of what was searched.

## Step 3. Read the embedded state, and expect padding

Changed 2026-10-01. The page embeds its own state as `window.__PRELOADED_STATE__` and renders from it. The reader takes the postings from there, because the rendered list only shows the age as German relative text such as `vor 1 Woche`, while the state carries an exact `datePosted`. Stepstone has no API in its network responses, so there is nothing to call.

Verified 2026-10-01 over 4 pages and 135 records. The state's ids and the rendered ids matched exactly in both directions, so nothing is lost by reading the state alone.

| Field | Source |
|---|---|
| id | `id`, the dedup key, same number as in `/stellenangebote--{id}` |
| title | `title` |
| company | `companyName` |
| location | `location` |
| posted at | `datePosted` |
| url | `url`, relative, appended to the host |

Postings are found by shape rather than by path, meaning any object carrying both an `id` and a `datePosted`, since a reshuffle of Stepstone's own state tree would otherwise silently return nothing.

`datePosted` comes either bare or with an offset, both measured, so it is stored verbatim and read downstream in either form.

`salary` is empty on every record and `isWorkFromHomePossible` appears on about a quarter, so neither is read.

Padding is unchanged. Sparse queries are still filled with other cities and bundeswide entries, and the exact timestamp is what makes dropping them precise.

Sparse queries are padded with relaxed results, meaning older postings, other cities and "bundesweit" entries, in markup identical to the genuine ones. The measured extreme was 40 cards shown for a query whose strict count was 2. Padding is dropped after the fetch by checking each card's posted-age and location, and is never treated as an error.

## Step 4. Paginate and check completeness

Increase `page` by 1 with a few seconds of pacing. Exhaustiveness was proven on a full cell at 100 collected against 97 claimed, for Kiel over 24 hours. The per-page invariant applies to the 25 genuine results. Promoted cards repeat across pages legitimately, measured at 25 cards with 24 new and a page-one to page-two overlap of 7 including padding.

## Operating notes

- No blocking incidents so far. The collector's standard statuses apply unchanged.
- Access uses the pipeline profile at `~/.playwright-profiles/jobs` with `channel="chrome"`, one browser instance at a time, headed under the pipeline-wide rule.
- Login state is `AuthCA`, an access token lasting about 15 minutes, re-minted on contact from `AuthCARefresh` which lasts about 90 days. A session check has to read the cookies after visiting the site, because checking before contact reports a dead session that is not dead.

# Indeed

Parked. A logged-in search loaded once on de.indeed.com, and two paced requests were enough to trigger a Cloudflare "Additional Verification Required" page. A human verification did not carry over to later automated loads. Challenges are never automated past, so Indeed either runs with a person present or stays out of the sweep.
