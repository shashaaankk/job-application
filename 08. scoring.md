# Who decides what

Four decisions, and three of them are made by a run.

| Decision | Made by | Where |
| --- | --- | --- |
| is this posting out of scope | the screen, deterministically | `scripts/screen.py` |
| does the posting suit him, and does his record suit it | one agent process per card, Antigravity by default | `scripts/score.py`, five concurrent, per the [scoring skill](skills/scoring/SKILL.md) |
| does this card get documents | the tier, A or B, inside his three caps | the `to apply` column |
| is this worth applying to | him, whenever he pleases | the `applied` column |

The screen rejects and does not rank. The tier ranks and rejects only on a knockout,
which is his own hard preference or rule. His review re-scores a card and that is not a negotiation, because he is the authority on what he
can do.

Scoring runs on Antigravity rather than Claude for one reason. A hundred cards costs
about 1.5 million Claude tokens, almost none of it the posting, because every card
re-reads his rules, preferences and profile. His Claude plan is Pro, so the Claude
budget is spent on the CV and the letter, which are the things he sends.

# How a preference field is handled
(the job gives me what I want)

Every field in [04. preferences](04.%20preferences.md) belongs to one class, and the
class decides what happens when a posting breaks it. Swapping in a different
preferences file means editing the coverage table below and nothing else.

| Class        | Meaning                                                     | On violation                                    |
| ------------ | ----------------------------------------------------------- | ----------------------------------------------- |
| Hard         | decidable from the posting or the card, no judgement needed | reject, reason logged                           |
| Judgement    | needs the description read and interpreted                  | flag on the card, never a rejection, never a grade |
| Ranking      | a want rather than a requirement                            | orders the review list, never rejects           |
| Search scope | shapes what gets searched, not a property of a posting      | no check                                        |
| Surfaced     | never enforced, he decides                                  | written as a question on the card               |

Only his own preferences can reject a posting. Nothing a job advertisement wishes for
is a hard filter, because a requirements list is written to attract and is routinely
inflated.

Four rules apply to every field.

1. Query enforcement is never trusted on its own. Portals return results outside what was asked for, so a field enforced at the query is checked again after the fetch.
2. A field the posting does not state is recorded as unknown. Unknown is not a violation and is never filled in by inference.
3. Every field has a row in the coverage table. A field with no row is an unenforced preference, and the card says so rather than passing over it.
4. The preferences file is read at run time and is the only source of values. Nothing downstream keeps a copy, so editing the file changes behaviour on the next run.

# Coverage

| Field          | Class        | At query | After fetch |
| -------------- | ------------ | --- | --- |
| Location       | hard         | native on all portals | `places.in_preferences`, which reads the country list straight out of the preferences file and resolves the posting's place through the gazetteer below |
| Workplace type | hard         | not sent | a fully remote posting is rejected. LinkedIn supplies the type at collection, the others need the description read |
| Roles          | judgement    | keyword, loose by design | `screen_title` requires one of the ten roles or eight domains in the title |
| Domains        | judgement    | never, no portal supports it | part of the same title check |
| Freshness      | hard         | native on all three portals, which all now carry a 24 hour form | an exact timestamp arrives in the ledger, so freshness is decided from `posted_at` without reading the posting |
| Reposts        | hard         | not possible | LinkedIn supplies a `repostedJob` flag at collection. The ledger fingerprint covers the rest |
| Compensation   | surfaced     | never sent, on any portal | Naukri supplies the band at collection, with `Not disclosed` recorded as stated rather than inferred from silence. It is never screened on |
| Seniority      | hard, on a stated figure | where the portal has a facet, which is employer-labelled and not trusted alone | the title is checked against rule 2, and a description stating more than five years is rejected. A posting that merely reads senior without saying so is flagged |
| Portals        | search scope | defines the sweep | none |

Portal parameters and how far each can be trusted are in
[07. searching](07.%20searching.md) and [09. lessons](09.%20lessons.md).

# The screen

Every rejecting rule lives in `scripts/screen.py` and nowhere else, so there is one
definition of what is out of scope. Each rule cites the rule number in
[06. rules](06.%20rules.md) that authorises it.

Two stages, cheapest first.

**The title stage** reads the title and the lister only, so it costs nothing. It is
generous by design, because a description now costs an anonymous request of about a
third of a second and this stage exists to avoid paying for thousands of them rather
than to decide fit.

**The description stage** is where the real screening happens. The two largest error
classes, a description naming none of his work and a stated years figure, are both
invisible in a title.

Measured on one sweep of 6817 postings. The title stage left 466 and the description
stage left 227, so the title stage is right about half the time.

## How a place is resolved

A portal writes the place as a town and often omits the country, so "Stockach" is
Germany and nothing in the string says so. Three sources answer it, in order.

1. The region list in `scripts/places.py`, holding countries, states and provinces. A region name is not a city and no city dump carries it, so this part stays hand written.
2. `scripts/data/gazetteer.tsv`, 565000 place names with their countries, built from the GeoNames `cities500` dump by `scripts/build_gazetteer.py`. It is committed, so a run downloads nothing and the screen stays deterministic. Rebuild it only when a place is genuinely missing.
3. The country the query asked for, read from the ledger's cell. This is used only when the first two resolve nothing, because a portal omits the country exactly when it is the local default. The card records it as taken from the query rather than read from the posting.

A name held by more than one country, such as Freiburg in Germany and Switzerland,
defaults to the more populous place and is overridden by the searched country only
when a place of that name genuinely exists there.

The hand written city list this replaced cost 88 postings in one run, every one a
German town, and the cards were never written. A list a person maintains cannot be
complete, so the screen no longer depends on one.

A posting that survives both stages becomes a card in the `matched` column, with the
screen's own reading written into the card's Evaluation section. That reading records
which roles the title named, which of his work areas the description named, and any
flags raised. It is not a grade and it says so on the card.

# How a ruling is enforced

A rule written into this file changes nothing on its own. Six postings reached the
board that he had already ruled out in principle, each one through a rule that
existed and was checked at the wrong stage or with too loose a pattern.

So every posting he rules on becomes a case. `scripts/data/screen-cases.tsv` holds
its ledger fields and points at its stored description, which makes the case offline
and exactly repeatable. `scripts/test_screen.py` runs the screen over every case,
and `make_cards.py` runs that first and refuses to build cards when any case fails.

Cases come in both directions, and the second kind matters as much as the first.

1. A `reject` case the screen keeps is a posting he has already said not to send.
2. A `keep` case the screen rejects is a rule of ours throwing away his field. Three of my own rules over-rejected on their first version, one over an agency's list of the sectors it staffs and one over the word desktop in a Qt and C++ role.

A keep case is run with its own country allowed. Otherwise removing a country from
the preferences makes every keep case in that country fail, which stops the run. It
did, on 13 October, after France came off the list.

The test also re-screens every card on the board and names any that a current rule
would now reject, so a new rule cannot quietly invalidate work already accepted.

# What a tier causes

The tier is the document trigger. The axes, the formula and the card layout are in the
[scoring skill](skills/scoring/SKILL.md). Tier A is band 3 and tier B is band 2, and
both generate a CV. Tier C is band 1 and stays in `matched` with its reason, so he
can overrule it. A knockout is band 0 and is pruned. A cover letter is not part of a run, per
rule 83, and is written only when he names a card and asks. A gate failure
generates nothing, since it produces no tier.

The preference match vetoes regardless of tier, so a hard violation rejects the
posting before the tier is consulted.

The card's tailoring edits are proposals, written as unticked boxes. No CV is built
until he ticks at least one, and only ticked edits are applied, per rule 83. The
must-have table is the first draft of the letter's bridge map.

Generation is capped per run at 20 cards at band 3, 30 at band 2, and 35 in total.
The caps are his, they bind generation alone, and the mechanics are in the
[scoring skill](skills/scoring/SKILL.md). Scanning, fetching, screening, scoring and
writing cards all stay uncapped, so the board receives every scored posting whatever
the caps do.

`score.py` applies the caps when it moves cards, so the limit binds at the column.
Every card is scored before any moves, then tier A moves before tier B. A card past the cap keeps its evaluation, stays in
`matched`, and is moved only when he moves it.

`scripts/pending.py` reads the `to apply` column and is the only authority on what
document generation acts on. It lists tier A work first and tests the `cv` key alone, and `--letters` lists the
cards with no letter yet. The procedure is in the
[artifact generation skill](skills/artifact-generation/SKILL.md), and a scheduled
task runs it nightly after scoring.

# Why the rejects are one table

The screen carried eight reject rules at the title and one admit rule at the
description. That asymmetry is the whole of the problem. A posting with a clean
title and one matching keyword in its description always passed, which is how a
mechanical CAE role, a defence vehicle role, a Windows desktop role, an insurance
group leader, a commodity trader, a web QA role and eleven controller and FPGA
postings all reached the board.

So the trades are a table in `screen.py` and the table runs at both stages. A new
ruling is a row in that table plus a case in `screen-cases.tsv`, never a patch at
one stage.

Each row carries two settings. `floor` is how many distinct terms are needed, since
one term can be a passing mention. `core_guard` waives the reject when the
description names one of his own disciplines, which separates a PLC role from a C++
role that talks to a PLC, and an FPGA design role from an embedded role whose board
happens to carry one.

His disciplines, for that test, are deliberately not the market words robotics,
automotive and aerospace. Those appear in every advert a company in that market
writes whatever it is hiring for, and reading a market word as evidence of his work
is the single error behind most of the postings he has had to point out.

# A flag is not a rejection

Two flags exist and neither one rejects.

1. A German language requirement at working level, per rule 6. It is written on the card and he decides.
2. An agency, consultancy or body-leasing lister, per rule 12, which is information only and is considered in every country like a direct employer.

# One thing worth repeating

A posting's requirements list is a wish, not a bar. The work it describes is the part
worth reading.
